## 1. Server streaming cho bản ghi có kiểu

Trả lời yêu cầu của phiên data-service + user-service
([`../ghi-chep/yeu-cau-server-stream.md`](../ghi-chep/yeu-cau-server-stream.md)).
**Cả ba chỗ chặn trong yêu cầu đều đã gỡ**, cộng một chỗ thứ tư mà yêu cầu không
nêu nhưng lại nằm đúng đường đi thật của họ (mục 1.4).

### 1.1. Phía server: `@stream` + `yield`

```python
from collections.abc import AsyncIterator

@stream("watch_changed_accounts")
async def watch_changed_accounts(
    self, request: WatchRequest
) -> AsyncIterator[AccountChanged]:
    async for event in self.feed.follow(request.after_sequence):
        yield AccountChanged(sequence=event.sequence, account_id=event.account_id)
```

Proto sinh ra **không có wrapper**:

```protobuf
rpc WatchChangedAccounts(WatchRequest) returns (stream AccountChanged);
```

`StreamKind.SERVER_STREAM_TYPED` là kind thứ tư; dạng byte (`DownloadStream` →
`*Chunk`) **không đổi một dòng nào**, đúng như yêu cầu xin.

Ba dạng khai sai báo lỗi lúc **khởi động**, không phải lúc gọi RPC đầu tiên:

| Viết sai | Thông báo |
| --- | --- |
| `@command` có `yield` | "@command must return one response, so it cannot be an async generator" |
| Vừa `DownloadStream` vừa `yield` | "@stream takes either an DownloadStream parameter or `yield`, not both" |
| Thiếu `-> AsyncIterator[<BaseModel>]` | "a typed server stream must be annotated `-> AsyncIterator[<BaseModel>]`" |

**Dọn dẹp khi client bỏ đi:** serving glue gọi `aclose()` trên generator của
handler, nên `finally:` của nghiệp vụ (đóng session DB, nhả khoá) chạy ngay lúc
client huỷ chứ không đợi thu gom rác. Có test canh đi thẳng vào handler
(`TestServingGlue::test_handler_generator_is_closed_on_cancellation`).

### 1.2. Phía client: SDK sinh ra iterator có kiểu

```python
async for event in client.watch_changed_accounts(WatchRequest(after_sequence=0)):
    revoke(event.account_id)          # DTO Pydantic, không phải bytes
```

`SdkRuntime.server_stream_typed()` marshal từng message y khuôn `unary`.
`server_stream()` cũ (rút `item.chunk`) giữ nguyên cho tải file.

Method sinh ra **không phải `async def`**: nó trả thẳng generator để người gọi
viết `async for` mà không phải `await` trước. Giống hệt `server_stream` cũ.

### 1.3. Deadline: chọn phương án (b) như yêu cầu khuyến nghị

```yaml
grpc:
  clients:
    user:
      deadline_ms: 3000          # call unary
      stream_deadline_ms: 0      # server streaming; 0 = không giới hạn (MẶC ĐỊNH)
```

**Đây là đổi hành vi cho cả luồng tải file**, không riêng luồng mới: trước đây
mọi server-stream chịu `deadline_ms`. Chấp nhận có chủ đích - một lần tải file
lớn qua đường chậm bị cắt sau 3 giây cũng là lỗi, chỉ là chưa ai gặp.

Kèm **keepalive** (mục 3.3 của yêu cầu, không bắt buộc nhưng đã làm) ở **cả hai
đầu**, mặc định TẮT:

```yaml
grpc:
  clients:
    user:
      keepalive: { time_ms: 30000, timeout_ms: 20000, permit_without_calls: true }
  keepalive:
    min_ping_interval_without_data_ms: 30000    # PHÍA SERVER
```

> Làm một đầu là bẫy: gRPC server mặc định chỉ chấp nhận ping cách nhau 5 phút,
> nhanh hơn thì trả GOAWAY `too_many_pings` - giết đúng luồng dài mà keepalive
> sinh ra để bảo vệ. Vì vậy phơi cả khoá phía server.
>
> `permit_without_calls: true` còn tự nới `grpc.http2.max_pings_without_data`
> (mặc định 2, tức là client ngừng ping sau hai lần khi không có dữ liệu - đúng
> lúc cần nó nhất).

### 1.4. ⚠ Chỗ chặn thứ TƯ mà yêu cầu chưa thấy: đường Java → Python

Yêu cầu ghi mắt xích đáng làm là **user-service (Java) phơi luồng → data-service
(Python) tiêu thụ**. Đường đó đi qua **fallback proto-only** của trình sinh SDK
(service Java không có `contract.json`), mà nhánh đó **bỏ qua mọi method
streaming**:

```python
if method.client_streaming or method.server_streaming:
    result.skipped_methods.append(path)      # code cũ
    continue
```

Nghĩa là sửa xong ba chỗ chặn kia thì data-service **vẫn không gọi được** luồng
của user-service. Nay fallback sinh **server-stream có kiểu** (mỗi message là DTO
của response); chỉ **client-stream** còn bị bỏ qua, vì quy ước upload của xime
cần sidecar mới biết message nào là wrapper metadata. Có test canh riêng
(`test_proto_only_fallback_generates_server_streams`).

Hệ quả phụ đáng biết: một proto **do xime sinh** mà tiêu thụ **không kèm**
`contract.json` thì rpc tải file nay sinh ra luồng yield `FooChunk` (model có
trường `chunk: bytes`) thay vì bị bỏ qua. Suy giảm hợp lý, không phải lỗi.

### 1.5. Còn lại là việc của người tiêu thụ, không phải của framework

Yêu cầu tự nêu (mục 4) và tôi xác nhận **giữ nguyên**: `XimeGrpcChannel` thay
channel khi cert mTLS xoay, ân hạn 30 giây, nên luồng dài **chắc chắn bị cắt
theo lịch cert**. Framework không tự nối lại - nó không biết con trỏ nằm ở đâu.
Khuôn "giữ con trỏ, bắt lỗi, nối lại từ con trỏ" đã viết vào tài liệu
`docs/{vn,en}/grpc-client.md` để người viết đầu tiên không tưởng luồng sống mãi.
Retry tự động vẫn **không** áp cho streaming, đúng như yêu cầu xin giữ.

### 2.2. Mức "cảnh báo" chọn thế nào

## 5. Quyết định thiết kế và đánh đổi

Ghi lại để phiên sau không "sửa lại cho đúng" thứ đã cân nhắc.

### 5.1. Vì sao handler là async generator, không phải `MessageStream.write()`

Cách đối xứng với `DownloadStream` sẽ là thêm một interface
`MessageStream.write(model)`. **Không chọn**, vì kiểu của message phải khai ở
đâu đó, và chỗ duy nhất tự nhiên là **annotation return**. Async generator cho
luôn ba thứ: kiểu nằm trong `-> AsyncIterator[Model]`, backpressure của gRPC
chạm thẳng code nghiệp vụ (không qua queue trung gian), và client huỷ thì handler
dừng ngay tại `yield` kế tiếp.

Đổi lại: `ContractBuilder` phải nới quy tắc "handler bắt buộc là coroutine" - vốn
là một fail-fast cố ý từ trước. Bù bằng ba lỗi khởi động ở mục 1.1, nên không có
dạng nào lọt xuống runtime.

### 5.2. Vì sao thêm `StreamKind` mới thay vì tái dùng `SERVER_STREAM`

Byte và bản ghi có kiểu khác nhau ở **hình dạng proto** (`*Chunk` wrapper hay
không), nên nếu gộp thì `_proto_emitter`, `_sidecar`, `_service_builder` và
`_codegen` đều phải đoán bằng cờ phụ. Một enum member đọc được ở cả bốn chỗ rẻ
hơn nhiều. Số chỗ phải sửa khi thêm kind: đúng 4 chỗ `if kind is ...`, đã sửa
hết.

### 5.3. Vì sao `stream_deadline_ms` mặc định 0 chứ không kế thừa `deadline_ms`

Phương án an toàn hơn về tương thích là để `None` = kế thừa `deadline_ms`. Không
chọn, vì phiên gửi yêu cầu khuyến nghị 0 và vì **deadline cho một luồng gần như
luôn sai**: `deadline_ms` được chỉnh để bắt call unary treo trong vài giây, còn
luồng thì sống theo nghiệp vụ. gRPC bản thân nó cũng không đặt deadline mặc định.

Rủi ro còn lại (luồng treo mãi trên kết nối đã chết) trả bằng keepalive ở mục
1.3 - đó là lý do làm luôn mục 3.3 dù yêu cầu ghi "không bắt buộc".

### 5.4. Vì sao `_INLINE_SAFE` là danh sách CHO PHÉP, không phải danh sách CẤM

Danh sách cấm (`text/html`, `image/svg+xml`, ...) luôn thiếu: `application/xhtml+xml`,
`text/xml`, kiểu lạ do backend trả về... Danh sách cho phép thì sai theo hướng
an toàn - cùng lắm là một kiểu hợp lệ bị ép tải xuống, sửa bằng cách thêm vào
danh sách sau khi cân nhắc.

`image/svg+xml` **cố ý nằm ngoài**. Đây là chỗ dễ bị "sửa lại cho tiện" nhất.

### 5.5. Vì sao F5 khớp theo TÊN khoá chứ không theo giá trị

`RuntimeConfig` cho phép khoá lạ (`extra: allow`), nên phần lớn secret nằm ở khoá
mà framework chưa từng nghe tên. Khớp theo tên (`secret/password/token/key/
credential`) che được cả những khoá đó. Đánh đổi: `server.ssl.keyfile` (một
đường dẫn) cũng bị che vì tên có "key". Chấp nhận - che thừa một đường dẫn rẻ
hơn lộ một khoá ký.

### 5.6. Vì sao localfs không dùng `chmod` sau khi ghi

`os.open(..., mode)` đặt quyền ngay lúc tạo; `chmod` sau khi ghi để hở một khoảng
thời gian file ai cũng đọc được. Với thư mục thì buộc phải `chmod` (mkdir bị
umask che), nên chỉ chmod thư mục **mới tạo** và nuốt `OSError` - Windows bỏ qua
phần lớn bit POSIX, không được để chuyện đó làm hỏng một lần ghi.

## 6. Cạm bẫy cho phiên sau

Sáu thứ đã vấp trong chính phiên này:

1. **Thuộc tính bắt đầu bằng gạch dưới trong model Pydantic thành `ModelPrivateAttr`.**
   Khai `_SENSITIVE = (...)` trong `RuntimeConfig` rồi lặp qua nó là
   `TypeError: 'ModelPrivateAttr' object is not iterable`. Phải để hằng ở **mức
   module**.
2. **PoC bảo mật không nhất thiết đi qua framework.** PoC 2, 3 dựng Starlette
   trần; PoC 11 không bắt log. Vá xong chạy lại vẫn thấy "THỦNG"/"im lặng" mà
   không phải vì bản vá sai. Đọc thân PoC trước khi kết luận.
3. **Thêm `options=` vào `secure_channel`/`insecure_channel` làm vỡ mock cũ.**
   `side_effect=lambda *a: ...` không nhận keyword. Không phải lỗi logic.
4. **Bộ test OPC UA đỏ theo tải máy**, không theo code (mục 0).
5. **`aclose()` trên generator của handler phải gọi tường minh.** Để GC dọn thì
   `finally:` của nghiệp vụ chạy muộn không xác định - với luồng theo dõi sống
   hàng giờ, đó là session DB bị giữ hàng giờ.
6. **YAML không có literal bát phân.** `file_mode: 0600` ra số **600 hệ mười**.
   Vì vậy `_parse_mode` đọc chuỗi theo bát phân, và tài liệu bắt viết có nháy.

## 7. Cách dùng nhanh

**Phơi một luồng có kiểu (service Python):**

```python
# api/grpc/account_controller.py
from collections.abc import AsyncIterator
from xime.core.contract import stream

class AccountController:
    server_id = "default"

    @stream("watch_changed_accounts")
    async def watch_changed_accounts(
        self, request: WatchRequest
    ) -> AsyncIterator[AccountChanged]:
        async for event in self._feed.follow(request.after_sequence):
            yield AccountChanged(...)
```

Rồi `xime grpc generate` như thường lệ.

**Tiêu thụ luồng (kể cả luồng của service Java):**

```bash
# copy .proto của service đích vào contracts/<id>/ rồi:
xime grpc client --proto contracts/user --out clients/user
```

```python
cursor = load_cursor()
while True:
    try:
        async for event in self._user.watch_changed_accounts(
            WatchRequest(after_sequence=cursor)
        ):
            handle(event)
            cursor = event.sequence
            save_cursor(cursor)
    except (RemoteServiceUnavailable, RemoteCallError):
        await asyncio.sleep(backoff())     # nối lại TỪ CURSOR
```

## Mục tiêu & nguyên tắc xuyên suốt

1. **Theo đúng pattern starter đã có.** Cả `cache` và `redis` phải giống
   `sqlalchemy`/`scheduler` về: cấu trúc file (`__init__.py` + `_*.py` private),
   `__all__` chỉ liệt kê class DI quản lý, đọc runtime config qua `RuntimeConfig`,
   đóng tài nguyên ở `pre_destroy()`.
2. **Interface tách khỏi backend.** `cache` chỉ định nghĩa Protocol + config;
   `redis` là MỘT implementation. Binding khai báo tường minh trong
   `config/dependency.py` của service (`CacheService -> RedisCacheService`),
   đúng `rules/interface-binding.md`.
3. **Framework chỉ cấp cơ chế, không ôm chính sách.** Với peer mTLS: lưu **sự
   thật thô** (CN đã verify) dưới key trung tính, fail-soft; authorization vẫn ở
   app.
4. **Không thêm dependency bắt buộc.** `redis` import `redis.asyncio` ở mức
   module private, giống cách `scheduler` import `apscheduler` lười - service nào
   không dùng thì không phải cài.

## Nhóm 1 - Cross-cutting: danh tính peer mTLS cho gRPC (rủi ro thấp, làm trước)

Hiện `RequestContextInterceptor` (`xime/adapters/grpc/interceptors/_context.py`)
chỉ set `request_id`. Socket adapter đã có tiền lệ lưu `peer_pid`/`peer_uid`
(`adapters/socket/_peercred.py`). Cần bản tương đương cho gRPC mTLS.

### 1.1 - Đọc CN client cert vào request_context

- File sửa: `xime/adapters/grpc/interceptors/_context.py`.
- Trong `_wrap_unary` / `_wrap_streaming`, `ServicerContext` là tham số thứ hai
  của handler (`args[1]` với unary, cũng `args[1]` với streaming -
  `(request, context)` / `(request_iterator, context)`). Từ đó gọi
  `context.auth_context()` -> dict `bytes -> list[bytes]`, lấy
  `b"x509_common_name"` (hoặc key `"x509_common_name"` tùy version grpc - thử cả
  hai, decode utf-8).
- **Fail-soft tuyệt đối:** không mTLS / không có CN / `auth_context()` ném ->
  KHÔNG set key, KHÔNG phá request. Bọc trong `try/except Exception`.
- Lưu dưới **key trung tính** `peer_cn` (KHÔNG đặt tên `caller_service_id` -
  CN có thể là service id HOẶC `owner_app_identity_id` của APPLICATION subject,
  app tự diễn giải; xem mô hình Subject ở CLAUDE.md gốc).
- Tách phần đọc CN ra một helper riêng `_read_peer_cn(context) -> str | None`
  trong cùng file để hai wrapper dùng chung và test được độc lập.
- Thứ tự không đổi: `RequestContextInterceptor` vẫn outermost
  (`_adapter.py:255`), set `request_id` + `peer_cn` rồi mới tới error mapping.

### 1.2 - Helper `current_caller()` ở core

- File: thêm vào `xime/core/security/` (đề xuất `_caller.py`), export qua
  `core/security/__init__.py`.
- Nội dung: `def current_caller() -> str | None: return request_context.get("peer_cn")`.
  Đặt ở `core/security` (không ở adapter) để code nghiệp vụ import trung lập với
  transport. Tài liệu hóa rõ: trả CN thô, app tự map sang định danh nghiệp vụ.
- Cân nhắc: hằng tên key `PEER_CN = "peer_cn"` đặt một chỗ để interceptor và
  helper dùng chung, tránh lệch chuỗi.

### 1.3 - Test

- `tests_temp/grpc/test_interceptors.py` (hoặc file mới
  `test_peer_identity.py`):
  - Có CN -> `request_context["peer_cn"]` đúng giá trị, `current_caller()` khớp.
  - `auth_context()` rỗng / không mTLS -> `peer_cn` không tồn tại,
    `current_caller()` trả `None`, request vẫn chạy bình thường.
  - `auth_context()` ném exception -> nuốt lỗi, request không hỏng.
  - Teardown vẫn `clear()` `peer_cn` cùng `request_id` (không rò rỉ giữa call).

## Nhóm 2 - Starter `cache` (interface caching dùng chung)

Làm trước `redis` vì `redis` phụ thuộc Protocol này.

### 2.1 - Cấu trúc

```text
xime/starters/cache/
  __init__.py        # export CacheService, CacheConfig (nếu cần)
  _service.py        # Protocol CacheService
```

### 2.2 - Protocol `CacheService`

- File: `xime/starters/cache/_service.py`, định nghĩa bằng `Protocol` (không
  `ABC`), async đầy đủ:
  - `async def get(self, key: str) -> bytes | None`
  - `async def set(self, key: str, value: bytes, ttl: int | None = None) -> None`
  - `async def delete(self, key: str) -> None`
  - `async def exists(self, key: str) -> bool`
- **Chốt kiểu value:** dùng `bytes` (thô, không tự serialize) để framework không
  ôm chính sách serialize - app tự encode/decode JSON/pickle tùy ý. Ghi rõ lý do
  trong docstring. (Nếu sau này cần tiện hơn, thêm lớp tiện ích ở 0.5+, không
  phá interface.)
- TTL đơn vị **giây**, `None` = không hết hạn. Tài liệu hóa.

### 2.3 - `__init__.py`

- `__all__: list[str] = []` (Protocol không được scanner đăng ký - giống
  `ScheduledJob`). Vẫn import `CacheService` để `from xime.starters.cache import
  CacheService` dùng được trong binding.

### 2.4 - Test

- `tests_temp/cache/`: một `FakeCacheService` (dict in-memory) thỏa Protocol ->
  assert `isinstance(fake, CacheService)` (Protocol runtime-checkable nếu cần)
  và round-trip get/set/delete/exists/ttl logic ở mức fake. Mục tiêu là chốt
  hình dạng interface, chưa cần Redis thật.

## Nhóm 3 - Starter `redis` (Redis client + impl của CacheService)

### 3.1 - Cấu trúc

```text
xime/starters/redis/
  __init__.py        # export RedisClientProvider, RedisCacheService
  _client.py         # RedisClientProvider: tạo + giữ pool, pre_destroy đóng
  _cache.py          # RedisCacheService: implement CacheService dựa trên client
```

### 3.2 - `RedisClientProvider` (vòng đời connection pool)

- File: `xime/starters/redis/_client.py`. Theo đúng khuôn `AsyncEngineProvider`
  (`starters/sqlalchemy/engine.py`):
  - `__init__(self, config: RuntimeConfig)` đọc:
    - `redis.url` (bắt buộc, ví dụ `redis://localhost:6379/0`) - thiếu ->
      `raise ValueError` rõ ràng (fail-fast).
    - `redis.max_connections` (tùy chọn, mặc định hợp lý vd 10).
  - Tạo client async (`redis.asyncio.from_url(...)`), giữ làm property `client`.
  - `async def pre_destroy(self)` -> `await self._client.aclose()` (đóng pool;
    khớp mục "Close Database / Redis / gRPC Channels" trong trình tự shutdown đã
    có ở thiết kế). LifecycleManager tự gọi vì có method `pre_destroy`.
- Import `redis.asyncio` ở đầu file private (chỉ nạp khi service scan package
  này), giống `scheduler/_runner.py` nạp apscheduler. KHÔNG import trong
  `cache/`.

### 3.3 - `RedisCacheService` (implement `CacheService`)

- File: `xime/starters/redis/_cache.py`.
- Constructor: `__init__(self, provider: RedisClientProvider)` - inject provider,
  dùng `provider.client`. (Inject provider chứ không inject raw client để vòng
  đời nằm gọn ở provider.)
- Cài đủ bốn method Protocol, map thẳng sang lệnh redis async
  (`get`/`set` kèm `ex=ttl`/`delete`/`exists`). Trả/nhận `bytes` đúng contract.
- KHÔNG kế thừa `CacheService` (Protocol, structural typing - không bắt buộc);
  framework validate khi binding lúc startup.

### 3.4 - `__init__.py`

- `__all__ = ["RedisClientProvider", "RedisCacheService"]` - cả hai là singleton
  DI quản lý (giống `AsyncEngineProvider`/`AsyncSessionFactory`).

### 3.5 - Binding (tài liệu hướng dẫn, không phải code framework)

- Trong `config/dependency.py` của service dùng:
  ```python
  dependency.scan("xime.starters.redis")
  dependency.bind({ CacheService: RedisCacheService })
  ```
- Framework tự inject `RuntimeConfig` vào provider, `provider` vào cache service.

### 3.6 - Test

- `tests_temp/redis/`: ưu tiên test KHÔNG cần Redis thật - mock `redis.asyncio`
  client (AsyncMock) và assert:
  - `RedisCacheService` thỏa Protocol `CacheService`.
  - get/set(ttl)/delete/exists gọi đúng lệnh + tham số trên client mock.
  - `pre_destroy()` gọi `aclose()`.
  - thiếu `redis.url` -> `ValueError` lúc khởi tạo provider (fail-fast).
- Nếu muốn integration test thật: đánh dấu skip khi không có Redis env (giống
  cách suite hiện bỏ qua test cần hạ tầng).

## Nhóm 4 - Cân nhắc thêm (CHƯA chốt cứng - quyết khi tới)

chặn việc phát hành phần starter:

### 4.1 - gRPC reflection + health checking (vận hành)

- Giá trị: `grpcurl`, load balancer, k8s liveness/readiness probe dùng được mà
  không khai báo tay.
- Hướng: bật `grpc_reflection` + `grpc_health.v1` qua một cờ trong cấu hình gRPC
  server (mặc định TẮT để giữ bề mặt nhỏ). Cần khảo sát thêm `_adapter.py` chỗ
  `grpc.aio.server(...)` để gắn service health/reflection trước khi `start()`.
- **Quyết định mở:** có nên bật mặc định không, health check map tới cái gì
  (chỉ "serving" tĩnh hay theo readiness thật của DI/adapter).

### 4.2 - Error catalog visibility-aware dùng chung (#1b)

- Đây là **quyết định kiến trúc**, không chỉ code - cần một phiên thiết kế riêng,

  class, adapter tự che lỗi không đủ quyền theo kênh).
- **Đề xuất:** KHÔNG nhồi vào 0.4. Hoặc tách thành mini-doc thiết kế trước
  (`docs/thiet-ke-error-catalog.md`), rồi mới gắn mốc. 0.4 chỉ nên ghi nhận và
  để mở. Cần xác nhận của bạn.
